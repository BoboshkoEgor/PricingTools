# eSIM A/B Lab

Учебная «коробка» для A/B-тестов на данных магазина eSIM. Сейчас готов **этап 1: база данных**.
В ней каталог и цены из реального кейса по ценообразованию, а поверх — синтетическая история
магазина: пользователи, сессии, воронка и заказы.

Ключевая идея проекта: A/B-платформа читает данные только через слой `contract`.
Синтетику можно заменить реальными логами, и платформу при этом переписывать не нужно.

## Архитектура

```
 Источник данных (канал 1)          Магазин                    A/B-платформа (этап 2)
 ┌──────────────────────┐   ┌──────────────────────────┐   ┌────────────────────────────┐
 │ xlsx с тарифами      │──▶│ raw → catalog, pricing   │   │ эксперименты, параметры,   │
 │ (или выгрузка ERP)   │   │                          │   │ история запусков (abp.*)   │
 └──────────────────────┘   │ shop: users, events,     │   │                            │
                            │       orders             │──▶│ читает только contract.*   │
 Поток действий (канал 2)   │                          │   │ считает p-value, ДИ, SRM,  │
 ┌──────────────────────┐   │ contract.* — представ-   │   │ CUPED → abp.results        │
 │ генератор / LLM-боты │──▶│ ления для платформы      │   │ → страница с результатами  │
 │ / реальные логи      │   └──────────────────────────┘   └────────────────────────────┘
 └──────────────────────┘
```

| Схема | Что лежит | Откуда |
|---|---|---|
| `raw` | Листы xlsx без изменений | `load_raw.py` |
| `catalog` | Направления, страны в пакетах, тарифы, журнал проблем данных | `sql/010_catalog.sql` |
| `pricing` | Цены по сценариям из файла, цены конкурентов, итоги кейсов | `sql/010_catalog.sql` |
| `pricing` (сценарий `baseline`) | Базовые цены по логике ноутбука | `loader/baseline.py` |
| `shop` | Пользователи, события воронки, заказы | `generate_history.py` |
| `sim` | Скрытые сегменты пользователей и параметры генерации | `generate_history.py` |
| `contract` | Представления, через которые читает A/B-платформа | `db/init/002_contract.sql` |
| `abp` | Пока пусто: эксперименты и результаты, этап 2 | — |

## Быстрый старт (Docker)

Нужен Docker Desktop.

```bash
# 1. Положите xlsx в папку data/ (он уже там, если вы распаковали архив целиком)
# 2. Поднимите базу и веб-интерфейс к ней
docker compose up -d

# 3. Загрузите данные (около 30 секунд)
docker compose run --rm loader
```

Во время загрузки скрипт пересчитывает Baseline по логике ноутбука и сверяет его
с листом `Cases_summary`: выручка 231 206,4 €, прибыль 61 546,5 €, маржа по группам,
доля ТОП-1 и «в рынке» совпадают.

В конце загрузки печатаются проверки. Число заказов по каждому тарифу совпадает с QTY,
выручка — с Baseline из листа `Cases_summary` (231 206,4 €):

```
  Заказов                          33090   ✓ совпадает с файлом
  Тарифов, где заказов ≠ QTY       0   ✓ совпадает с файлом
  Выручка заказов, €               231206.4   ✓ совпадает с файлом
  Себестоимость, €                 169659.9   ✓ совпадает с файлом
```

**Подключение к базе**

| Где | Параметры |
|---|---|
| Adminer в браузере | http://localhost:8080 → Система: PostgreSQL, сервер `db`, пользователь `esim`, пароль `esim`, база `esim` |
| DBeaver, DataGrip, psql | хост `localhost`, порт `5433`, база/пользователь/пароль `esim` |

Готовые запросы для первого знакомства лежат в `sql/examples.sql`.

**Если образы не скачиваются.** Docker Hub из России иногда работает медленно или недоступен.
Настройте зеркало реестра в Docker Desktop: Settings → Docker Engine → `registry-mirrors`.

## Без Docker

Подойдёт любой Postgres 14+ и Python 3.11+.

```bash
pip install -r loader/requirements.txt
export DATABASE_URL=postgresql://USER:PASSWORD@localhost:5432/DBNAME   # Windows: set DATABASE_URL=...
python loader/run_all.py --xlsx data/Pricing_analyst_task_PY_3cases.xlsx
```

Скрипт сам создаст схемы. Повторный запуск полностью пересобирает данные.

## Пересчёт Baseline

`loader/baseline.py` — отдельный скрипт. Он читает тарифы из `raw.all_prices_reduced`
и записывает цены сценария `baseline` в `pricing.prices`. Логика перенесена из ноутбука
`esim_pricing_FINAL.ipynb` (раздел 2.2):

1. целевая цена = себестоимость / (1 − маржа): 30% для 1–10 ГБ, 20% для 20+ ГБ и безлимита;
2. округление до ближайшей цены формата X,Y9, но не ниже себестоимости;
3. правила сетки: больший пакет дороже меньшего, цена за ГБ не растёт с объёмом;
   бессрочный пакет считается от 30-дневного той же страны и объёма.

```bash
docker compose run --rm loader python loader/baseline.py              # пересчитать и записать
docker compose run --rm loader python loader/baseline.py --dry-run    # только сверить с файлом
docker compose run --rm loader python loader/baseline.py --margin-small 0.32 --margin-big 0.22
```

Без Docker то же самое: `python loader/baseline.py ...`. Пересчёт меняет только цены
сценария `baseline`: каталог, история и заказы остаются как были.
Сверка с `Cases_summary` выполняется, когда маржа стандартная (30/20).

**Цены в магазине.** Витрина и история продаж живут на Baseline (`is_live = true` в
`pricing.scenarios`). Итоговые рекомендованные цены лежат в сценарии `recommended`:
это кандидат в вариант B для первого A/B-теста. Построить историю на других ценах:
`python loader/run_all.py --history-prices recommended` — выручка сверится с нужным сценарием.

## Что сгенерировано и какие допущения

Из файла взяты: 2 348 тарифов, 193 направления, себестоимость, цены 4 сценариев (+ Baseline из ноутбука),
цены конкурентов и продажи (QTY). Генератор достраивает то, чего в файле нет:

| Параметр | Значение | Где поменять |
|---|---|---|
| Период истории | 01.08–31.10.2026 (в файле период продаж не указан) | `PARAMS["start"]`, `["days"]` |
| Цены продаж | сценарий `baseline` (на витрине) | `--history-prices` (`baseline`, `recommended`, `conservative`, `medium`, `aggressive`) |
| Конверсия чекаута | 55% | `checkout_conversion` |
| Просмотр направления → клик «Купить» | 16% | `destination_to_click` |
| Возвраты | 1,5% заказов | `refund_rate` |
| Сегменты | budget, tourist, explorer, business: разная чувствительность к цене и частота покупок | `PARAMS["segments"]` |

Итог: ~89 тыс. пользователей, ~442 тыс. сессий, ~799 тыс. событий, 33 090 заказов,
конверсия сессии в покупку 7,5%. Генерация детерминирована: `--seed` даёт воспроизводимый результат.

**Найденные проблемы в исходном файле** (таблица `catalog.load_issues`):
- у 260 безлимитных тарифов нет SKU — сгенерированы SKU вида `AU-UNL-10D`;
- у Республики Конго в COVERAGE указан код Катара (QA), а SKU указывает на CG — взят код из SKU;
- пакет ASIA_26 записан под двумя названиями: «Asia 26» и «Asia».

## Как подменить данные на реальные

- **Канал 1, исходные данные.** Загрузите свой каталог в `catalog.*` и `pricing.*` или
  пересоздайте представления `contract.products` поверх своих таблиц.
- **Канал 2, действия пользователей.** Пересоздайте `contract.events`, `contract.orders` и
  `contract.users` поверх реальных логов с теми же колонками. A/B-платформа ничего не заметит.

Схема `sim` в реальном режиме остаётся пустой: скрытых сегментов у настоящих пользователей нет.
